57. **「设备树缺 interrupt-controller 节点」被证明是一个不承重的缺口，而它此前被当成剩余阻断列着**（2026-10-26， teammate `gic-adt` 的证据）：`implementation-plan.md:51` 的 WP04 一行把「以及设备树缺 interrupt-controller 节点」与根卷未挂载并列为剩余阻断。**该缺口是惰性的**：合成 ADT 里没有 GIC distributor 节点只让 `pe_arm_map_interrupt_controller` 记一条 `failed to find the interrupt-controller.`，而 `qemu_root_defconfig` 的 `CONFIG_XNU_NATIVE_VIRTIO_BLOCK` 走的是 virtio-mmio 的中断路径，不经它。**这条记下来是因为它是一个「被写进计划的未测量结论」的实例**：一行日志加一个「会挡后面」的猜测，就被提升成了与真实阻断并列的条目，而没有任何一次运行测量过它是否挡住任何东西。**顺带更正**：事实 38 末尾「与根卷无关但会挡后面」的措辞同样应当读作「已证明不挡」。

59. **本机 QEMU TCG 上第一次把真正的 iPadOS OS 卷挂起来了，而且 PID 1 已经出现——内核等的那个卷 UUID 逐字符对上**（2026-10-26，证据 `local-private/boot16/run1/`）：用 bundle 9 的 `qemu_root_defconfig` 内核（sha256 `7028fec147240e9a…`，279,660 个符号）+ 本机解出的 OS 卷 + `probe-root-volume.py` 启动，内核日志给出完整链条：`nx_mount: checkpoint search: largest xid 418, best xid 418 @ 3` / `BSD root: disk1s1, major 1, minor 3` / `apfs_vfsop_mountroot:2965: apfs: mountroot called!` / `handle_mount:817: disk1s1 vol-uuid: 04769D26-2CA0-4825-B443-E2E5F88300F2 block size: 4096 block count: 1483776` / `apfs_log_op_with_proc:3091: disk1s1 mount-complete volume DawnUpdate21H461.J120J121J207J208OS`。**挂载走的是 `NativeVirtioBlock`**（`IOService:/ArmDTPlatform/virtio-mmio-31@2003E00/NativeVirtioBlock/IOBlockStorageDriver/...`），也就是只有 `qemu_root_defconfig` 才有的那个驱动——所以量到的确实是新内核。**活访客进程表同时读到 `{"name": "init", "pid": 1, "state": "run"}` 与 `kernel_task` pid 0**，即 XNU 的 `bsd_init` 已经作为 PID 1 在跑。**本机解出的 OS 卷是自相一致的真容器**：GPT `EFI PART`、一个 `7c3457ef-…`（Apple_APFS）分区、容器 magic `NXSB`、block_size 4096、block_count 1,483,776（正好等于分区字节数 6,077,563,392），checkpoint 搜索也拿到了最大 xid——所以「挂不上」不是解码错，纯 Python 的 UDIF→raw 解码在去掉那 19 块 `n_literals=4 / n_literal_payload_bytes=0` 的拒绝对待之后（事实 15 之后 `lzfse.py:383` 明确不再拒）跑完了 6,077,580,800 字节。**这仍然不是「原始 launchd PID 1」**：进程名是 `init` 而不是 `launchd`，说明 `bsd_init` 还没有 exec 成功；而且这次启动**没有带 trust cache**。下一层阻断已精确定位，见事实 60。

60. **挂上之后挡 launchd 的是设备树缺两个属性，而不是缺镜像、缺内核或缺驱动**（2026-10-26，证据同事实 59 的 kernel.log）：日志顺序是 `import_iboot_forwarded_roothash:3491: importing root hash (basesystem ? 0)` → `apfs_extract_root_hash_arm:13275: could not retrieve system-volume-auth-blob from device tree` → `apfs_extract_root_hash_and_manifest failed with error: No such file or directory (2)`，然后挂载阶段 `fs_lookup_root_snapshot_name:373: disk1s1 failed to get root-snapshot-name from DT` → `apfs_find_named_root_snapshot_xid:2035: disk1s1 failed to retrieve default root snapshot xid: No such file or directory (2)` → `apfs_vfsop_mount:2714: disk1s1 failed to find named root snapshot: Need authenticator (81)`。**也就是说：卷挂上了，但挂的是卷的活动根，不是签名快照**——iOS 17 的 OS 卷是 SSV，`/sbin/launchd` 住在快照里，所以 exec 无从发生，PID 1 停在 `init`。**两个被钉死的仓库里没有任何脚本产出这两个属性**：`make-dt.py` 只支持 `--root-match-volume-uuid`（`:88-93` 生成 `/chosen` 的 `root-matching` XML）与 `--trust-cache`（`:162` 生成 memory-map 的 `TrustCache` sidecar 绑定），`build-os-root.py` 全文没有 `snapshot` 或 `auth` 字样。**这是 QEMU 这条路上一个真实的、可动的缺口**：真机上这两个值由 iBoot 放进设备树，而 QEMU 没有 iBoot，只有 ADT。**下一步就是取到这两个值**（快照名要从 APFS 卷的快照元数据里读，auth blob 要从 IPSW 的 `Cryptex1,SystemTrustCache`/manifest 侧取），而不是继续造构建侧的东西。**如实记录：这两个值的来源尚未查明，本条只是把阻断钉死在这里。**

61. **真机 j120 的设备树拿到了，而它证明 QEMU 的 ADT 缺的不只是快照名——`/chosen` 里有一整个真实属性集，模板树的值为零但名字是真的**（2026-10-26，本机证据 `F:/unipad-tmp/apple-dtre.bin`）：`local-private/out/components/DeviceTree.j120ap.im4p` 的 payload 是一串 `bvx2`（LZFSE）块——与 DMG 的 chunk 同一种格式——用本仓库自己的 `lzfse.lzfse_decompress` 解出 **172,392 字节**，247 个节点、2,732 个属性、1,110 个不同的属性名。**解它的时候踩到 Apple 的 ADT 与 `make-dt.py` 写的那一种的一个真实差别：属性长度字段带 0x80000000 标志位**，掩码之后解析正好消耗完全部 172,392 字节（不掩码则第二十条属性就越界）；仓库自己的 `adt.py:_parse` 不掩码，所以它解析 `make-dt.py` 的产物完全正常、解析真机树则报 truncated——这不是解码错，是两种树的编码差异。**真机 `/device-tree/chosen` 上有这些，而 `make-dt.py` 一个都不产出**：`consistent-debug-root`、`root-matching`（256 字节）、**`amfi-allows-trust-cache-load`**、`crypto-hash-method`（值 `sha2-384\0`）、`boot-manifest-hash`（48 字节）、`osenvironment`（32 字节）、`system-trusted`；根节点上还有 `secure-root-prefix`（值 `md\0`）。**这些值在模板树里全是零**——它是 IPSW 里的 EmbeddedDeviceTrees 模板，iBoot 在真机启动时填值——所以它证明的是「属性名存在、QEMU 侧缺失」，而不是「值是多少」。**两条直接后果**：(a) `amfi-allows-trust-cache-load` 与事实 56 做的 trust cache 直接相关，AMFI 很可能要看到它才允许加载，所以「文件摆上 ESP」与「AMFI 认账」是两件事；(b) `make-dt.py` 只支持 `--root-match-volume-uuid` 与 `--trust-cache` 两个开关（`:88-93`、`:162`），上面这些它一个都没有对应参数——这是被钉死的设备仓库的一个真实缺口，与事实 60 的快照名同一类。**仍未闭合**：`root-snapshot-name` 与 `system-volume-auth-blob` 在真机模板树里**同样不存在**，所以事实 60 说的「内核从 DT 读快照名」只是一条 fallback 路径，主路径另有来源；来源尚未查明。

62. **「再等等也许就好了」这个假设被关掉了：七分钟里内核日志一个字节都没长，PID 1 一直停在 `init`**（2026-10-26，证据 `local-private/boot16/watch2/`）：事实 59 的测量只看到第 19 秒——因为 `probe-root-volume.py` 的 `MARKERS` 里有 `"Waiting on"`，内核 16.7 秒就打这一行，于是 `--seconds 150` 也只在第一次观测后就退出。**「launchd 没有 exec」和「launchd 还没 exec」在这个观测窗口里分不开**，而这是当时最关键的区别。补测：`local-private/firmware/watch-root-guest.py` 用 probe 自己 `command.txt` 里的 argv 启动同一台机器（不手写 argv），然后每 60 秒观测一次活访客。**结果：7 次观测、跨度约 7 分钟，kernel log 一直是 22,576 字节（sha256 都不变），进程表一直是 `init` pid 1 + `kernel_task` pid 0。** 内核确实卡住了，不是慢。**这个补测本身也踩了两个自己的坑，都记着**：(a) 第一版把旧的 `tcp:...` 元素先过滤掉再写新的，于是 `index("-qmp")+1` 落到 `-serial` 上，QMP 端点覆盖了 flag，QEMU 报 `none: Could not open 'none'`——一个把argv 弄坏了的 harness 什么也量不到；(b) 第二版忘了 `mkdir`  run 目录，以及第一次观测没等内核加载行（`guestobserve` 会以 `evidence_incomplete` 拒）。**顺带一个结论**：事实 60 定位的两个 DT 属性缺失依然在日志里，但**快照元数据树是空的**（snapmeta 根块 `btn_nkeys=0`），所以「卷上没有快照」这件事与「内核要快照」同时成立——缺的不是取值方式，是卷里根本没有这个东西。OS 卷的 APSB 有 5 个（全是 xid 1026、type 0x0d），卷 omap 在物理块 67545（type 0x4000000b），extentref 树 oid 0x10810（subtype 0x0f）、snapmeta 树 oid 0x1082d（subtype 0x10）——树在，记录为零。
